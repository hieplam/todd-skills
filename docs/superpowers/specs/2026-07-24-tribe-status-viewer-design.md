# Tribe status viewer + `~/.tribe` campaign home — design

**Date:** 2026-07-24 · **Status:** approved by owner (this session) · **Owner decisions embedded below are rulings, not suggestions.**

## 1. Problem

Two observability gaps, both verified live on 2026-07-24:

1. **A human observer cannot see campaign-runner status.** The runner's report contract
   (`campaign-report.json`) is written **only on exit** — mid-run, status must be derived from
   the state JSON + `.runner.lock` + log growth, which nobody does by hand. Real incident: the
   owner believed **two** runners were running in parallel; `pgrep` showed **one** (pid 27542,
   `least-effort-5` in `ai-dict`) — the other campaign (`onboarding-category-c`) had exited
   `2026-07-17` with `reason: session_incomplete` and a week-old `STOP` file. There was no way
   to see this without shell forensics.
2. **The plugin disagrees with itself about where operational artifacts live.** The agents'
   convention is the machine-local home `~/.tribe/<repo-key>/…` (`agents/hunter.md:48`,
   established by commit `4393e44` "stop tracking operational state (moved to ~/.tribe)"). The
   campaign runner ignores it: `core/brief.ts:39-41` hardcodes
   `.claude/state/${campaign}/reports/${cardId}.md` into every executor brief — inside a module
   whose own header claims "no … paths … are hardcoded here (stateless-capability wall)". Result:
   worker reports land in the target repo's git working tree (live proof:
   `ai-dict/.claude/state/least-effort-5/reports/C1.md`), the exact thing `4393e44` moved out —
   and the reason `.claude/state/` had to be prettier-ignored (Partners PR #142 pain, same class).

## 2. Goals / non-goals

**Goals**

- A local, **read-only**, refresh-based web page answering at a glance: which campaigns exist,
  is each runner *actually* alive, per-card status, pending escalation questions, what the
  current executor session is doing right now.
- Scale to N parallel runner instances with zero per-instance viewer config.
- Fix the runner/agents inconsistency: campaign operational exhaust moves to the `~/.tribe`
  home — **injected as an input**, never hardcoded (wall W1 / skill-authoring anti-goal #1).
- A migration script for artifacts already written to the old hardcoded location.

**Non-goals (owner anti-goals)**

- No realtime push (websockets/SSE). Refresh **is** the poll.
- No writes of any kind by the viewer: no lock, no state, no `gh`/`git`/network calls.
  Disk truth only, labeled as such ("as recorded on disk; GitHub is authority", README §D4).
- No re-alignment of the *agent-dispatch* report convention (`hunter.md:48`
  `~/.tribe/<repo-key>/reports/<card-slug>.md`, no `campaigns/` level). Campaign-spawned
  executors receive `REPORT_PATH` explicitly in the brief, so nothing conflicts; aligning the
  agents' convention to the campaign tree is a **separate follow-up card**.

## 3. Owner decisions (recorded from this session's Q&A)

| # | Decision | Ruling |
|---|---|---|
| D1 | Status depth | Cards + runner liveness + **session activity tail** (full depth) |
| D2 | Discovery | Runner records itself under `~/.tribe`; viewer scans the tree — no registry file, no viewer config |
| D3 | Viewer shape | Bun server, **server-rendered HTML**, zero build step, zero client JS |

| D6 | Migration | Ship a migration script for the old `.claude/state/<campaign>/reports/` artifacts |

## 4. The `~/.tribe` campaign layout (the contract everything else hangs off)

```
~/.tribe/<repo-key>/                      ← repo key from tribe-home.sh (single source of truth)
  campaigns/<campaign-slug>/              ← stable campaign home  (= the runner's --home input)
    reports/<cardId>.md                   ← per-CARD worker reports; survive across runs
    runs/<run-id>/                        ← one folder per runner invocation
      run.json                            ← the run record (schema below)
      logs/…                              ← this invocation's session logs (default --logs-dir)
```

- `<run-id>` = `<ISO8601 basic timestamp>-<4 hex chars>` (e.g. `2026-07-24T06-13-59-a1b2`),
  generated by the runner at start. Unique per invocation; collision-safe enough at this rate.
- **What stays in the target repo (committed campaign memory — unchanged):** `state.json`,
  `answers.md`, `escalations/`, `campaign-report.json`/`.md`, `.runner.lock`, `STOP`.
  Rationale: "the loop belongs to the tribe, the memory belongs to the project" (runner README);
  git-carried memory is what lets a fresh machine resume a campaign. The lock stays keyed to the
  state file — the actual shared resource — so mutual exclusion cannot be defeated by two
  callers passing different `--home` values.

### `run.json` schema (v1)

```json
{
  "v": 1,
  "runId": "2026-07-24T06-13-59-a1b2",
  "pid": 27542,
  "startedAt": "2026-07-23T23:13:59.771Z",
  "repo": "/abs/path/to/target-repo",
  "statePath": "/abs/path/to/state.json",
  "answersPath": "/abs/path/to/answers.md",
  "escalationsDir": "/abs/path/to/escalations",
  "logsDir": "/abs/path/to/home/runs/<run-id>/logs",
  "argv": ["--cards", "C1,C2", "--max-cards", "1"],
  "endedAt": null,
  "exitCode": null,
  "reason": null
}
```

Written **atomically (temp + rename)** right after the lock is acquired (`endedAt`/`exitCode`/
`reason` null = in flight); finalized on every exit path that today writes the report, plus
best-effort in the same top-level catch that produces `reason: "error"`. Never deleted — the
`runs/` history is the campaign's machine-local audit trail. A `run.json` left with
`endedAt: null` and a dead pid is how the viewer detects a crash.

## 5. Runner changes (`plugins/tribe/scripts/runner/`)

1. **New required flag `--home <dir>`** — the campaign's machine-local operational home
   (absolute, or resolved against cwd). No default (D5). Missing flag = usage error, exit 1,
   same as `--answers` today. `--dry-run` continues to touch **nothing**: no run.json, no
   `<home>` directory creation (zero-side-effects contract holds).
2. **Run record:** generate `runId`, `mkdir -p <home>/runs/<run-id>/`, write `run.json`
   (atomic) after lock acquisition; finalize on exit. Refused starts (`EXIT_LOCKED`) write
   nothing (symmetry with the report contract: a refused process never creates artifacts).
3. **Delete `brief.ts:39-41`'s hardcode.** `reportPathFor` takes the home as a parameter:
   `REPORT_PATH = <home>/reports/<cardId>.md` (absolute — executor sessions run with
   `cwd = --repo`, so a repo-relative path can no longer express this). `brief.ts` stays pure;
   the home arrives via its existing caller in `loop.ts`/`card-actions.ts`.
4. **`--logs-dir` default moves** from "`logs/` next to the state file" to
   `<home>/runs/<run-id>/logs/`. Explicit `--logs-dir` still overrides (back-compat for the
   orchestrate-campaign invocations that pass it today).
5. **Ports/adapters:** the run-record write goes through the existing `FsPort`-style seams
   (`ports/ports.ts`); no core module imports `fs` (structure.test.ts keeps enforcing this).
6. **README:** new flag row, run-record contract section, updated logs-dir default, updated
   worked example.

## 6. orchestrate-campaign skill changes

- Stage-A / trigger sections gain the injection step:
  `--home "$(plugins/tribe/scripts/tribe-home.sh <target-repo>)/campaigns/<campaign-slug>"`.
  `tribe-home.sh` remains the **only** place that knows the `~/.tribe` key derivation
  (anti-goal #3: one source of truth; the runner never learns `~/.tribe` exists).
- The skill's runner-contract table adds `--home` as required.

## 7. Viewer (`plugins/tribe/scripts/viewer/`)

A sibling capability to the runner, same stack (bun + TS) and same seam discipline.

**CLI:** `bun plugins/tribe/scripts/viewer/serve.ts [--tribe-root <dir>] [--port <n>]`
- `--tribe-root` defaults to `$HOME/.tribe` (derived from the `HOME` env var — mirrors
  `tribe-home.sh`'s own convention; overridable for tests and non-standard setups).
- `--port` defaults to `4321`. Binds `127.0.0.1` only.

**Request flow (every GET `/` — refresh = re-poll, nothing cached):**

1. Scan `<tribe-root>/*/campaigns/*` → campaign dirs.
2. Per campaign, read (each read individually fault-isolated):
   - all `runs/*/run.json` → latest by `startedAt`;
   - liveness: latest run has `endedAt: null` → `process.kill(pid, 0)` probe (signal 0 — the
     same read-only probe the runner's own lock reclaim uses) → **RUNNING** (alive) /
     **CRASHED** (dead pid, run never finalized); latest run finalized → **EXITED (reason,
     exit code)**; no runs at all → **NEVER RUN**;
   - via `run.json`'s recorded absolute paths: the state JSON at `statePath` (card table),
     `.runner.lock`/`STOP`/`campaign-report.json` next to it, and escalation files under
     `escalationsDir` — no path guessing; the run record carries every location the runner
     was actually invoked with;
   - session activity: newest file under the latest run's `logs/` → size, mtime,
     **seconds-since-last-write** heartbeat, last ~40 lines (tail, HTML-escaped, truncated);
   - worker reports: `reports/*.md` listing per card (rendered as expandable text).
3. Derive `StatusModel` (pure), render HTML (pure), respond.

**Page structure:** one page, one section per campaign — header (campaign, repo, liveness
badge, runId, started/ended, STOP banner if present), card table (status, PR#, `updatedAt`,
`blockedOn`), pending escalations with the question text inline, session tail in a `<pre>`,
report links. Campaigns sorted: RUNNING first, then CRASHED, then by last activity.

**State parsing is tolerant, deliberately unlike the runner's.** The runner refuses malformed
state loudly (correct for a writer). The viewer must render *around* damage (correct for an
observer): a card panel it can't parse renders as an error panel with the raw reason; the rest
of the page renders normally. The viewer therefore has its own lenient reader (read fields
defensively, never `parseState`'s throwing validation) — this is a contract choice, not code
duplication.

**Honest-labeling rule:** every status the viewer shows is disk-derived. The page header states:
"Read-only view of on-disk state. GitHub (`gh pr view`) is authority for PR/merge truth."

## 8. Migration script (`plugins/tribe/scripts/migrate-campaign-home.sh`)

Follows the existing `migrate-state.sh` pattern (bash strict mode, test alongside).

- **Inputs (nothing hardcoded):** `<target-repo>` (required), `--campaign <slug>` (optional —
  default: every campaign found), `--dry-run` (print moves, touch nothing).
- **What it migrates (deterministic, because the old path was hardcoded):**
  `<repo>/.claude/state/<campaign>/reports/*.md` →
  `$(tribe-home.sh <repo>)/campaigns/<campaign>/reports/` (via `tribe-home.sh`, never its own
  key derivation). Creates target dirs; refuses to overwrite an existing target file (prints a
  conflict instead); removes emptied source dirs.
- **What it deliberately does NOT migrate:** old session logs — their locations were caller
  chosen (`--logs-dir`, e.g. `.okra/runs/...`), so there is no deterministic source to scan.
  The script prints a reminder listing the campaigns it touched so the owner can move logs by
  hand if wanted.
- Refuses to run while that campaign's `.runner.lock` pid is alive (never migrate under a
  live runner).

## 9. Error handling summary

| Failure | Behavior |
|---|---|
| `--home` missing (runner) | Usage error, exit 1, nothing written |
| run.json write fails | Runner logs a warning and continues — observability exhaust must never kill a campaign run |
| Viewer: unreadable run.json / state / logs | Per-campaign error panel; page always renders |
| Viewer: tribe-root absent/empty | Friendly empty page ("no campaigns recorded yet") |
| Migration: target exists / live lock | Refuse that item loudly, continue others, non-zero exit |

## 10. Testing

- **Runner:** unit tests through existing loop-test mocks (run record written after lock,
  finalized per exit path, absent on `--dry-run`/`EXIT_LOCKED`; brief `REPORT_PATH` uses the
  injected home; logs-dir default derivation). `structure.test.ts` keeps passing (no new
  world-imports in core).
- **Viewer:** `deriveStatus` + `renderHtml` are pure — fixture-snapshot tests: live runner,
  crashed (stale unfinalized run + dead pid), exited-with-report, escalation pending,
  unreadable state, empty tribe-root. One thin adapter test for the tree scan.
- **Migration:** `scripts/tests/test-migrate-campaign-home.sh` (fixture repo, dry-run parity,
  conflict refusal, live-lock refusal) — same style as `test-migrate-state.sh`.
- **Live smoke before trusting (README's own discipline):** one real runner invocation with
  `--home`, confirm run.json + reports + logs land in `~/.tribe`, open the viewer against it.
- Repo rule: `install.sh` updated if anything new needs linking (expected: nothing — viewer and
  migration script are repo-invoked like the runner; verify at implementation time).

## 11. Risks / known limitations

- **Viewer liveness is pid-based:** pid reuse can theoretically show a recycled pid as RUNNING.
  Accepted (same trade-off the runner's lock reclaim makes); mitigated by also showing the
  log heartbeat — RUNNING with a silent-for-an-hour log is visibly suspect.
- **In-flight campaigns during rollout:** a runner process started before this change keeps its
  in-memory code and old report paths until it exits (runs are one process per trigger, e.g.
  `--max-cards 1`); the migration script is run after it exits.
- The `hunter.md:48` agent convention divergence stands (non-goal; follow-up card).
